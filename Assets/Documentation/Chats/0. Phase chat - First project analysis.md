## Recommended Architecture for Catan

### 1. Core Architecture Pattern: Manager-Based with Service Locator

Use a Manager-based architecture with a Service Locator for dependency access:

- GameManager: orchestrates the game loop and state transitions
- PlayerManager: manages players, turn order, active player
- ResourceManager: handles resource collection, distribution, inventories
- BuildingManager: validates and places buildings (settlements, cities, roads)
- TradingManager: handles player-to-player and port trading
- DiceManager: manages dice rolls and triggers resource distribution
- UIManager: updates UI based on game events
- VictoryManager: tracks victory points and win conditions

Why this approach:
- Clear separation of responsibilities
- Easy to test and extend
- Scales as features are added
- Fits turn-based gameplay

### 2. Game Loop Structure

Use a state machine for game phases:

```
Initialization → Setup Phase → Main Game Loop → End Game

Setup Phase:
  - First Settlement Placement (all players)
  - First Road Placement (all players)
  - Second Settlement Placement (reverse order)
  - Second Road Placement (reverse order)
  - Initial Resource Distribution

Main Game Loop (per turn):
  1. Roll Dice Phase
  2. Resource Distribution Phase
  3. Robber Phase (if 7 rolled)
  4. Building Phase (player actions)
  5. Trading Phase (optional)
  6. End Turn → Next Player
```

State machine benefits:
- Clear phase transitions
- Prevents invalid actions
- Easy to add phases (e.g., development cards)
- Supports replay/undo

### 3. Event System: EventBus vs Unity Events

#### Unity's Built-in Event System

Unity Events (`UnityEngine.Events`):
- Pros:
  - Native, no custom code
  - Inspector assignable
  - Serialization support
  - Good for simple UI callbacks
- Cons:
  - Less flexible for complex systems
  - Inspector assignment can be tedious
  - Harder to debug (no centralized logging)
  - Not ideal for many-to-many communication

Unity Events are best for:
- UI button callbacks
- Simple component-to-component communication
- Inspector-driven connections

#### Custom EventBus Pattern

EventBus (custom implementation):
- Pros:
  - Decoupled communication (systems don't know each other)
  - Centralized event logging/debugging
  - Easy to add/remove listeners
  - Type-safe with generics
  - Can queue events, filter, prioritize
  - Better for complex game systems
- Cons:
  - Requires custom implementation
  - Can hide dependencies (harder to trace)
  - Risk of overuse

EventBus is best for:
- Cross-system communication (e.g., DiceManager → ResourceManager → UIManager)
- Game state changes
- Player actions affecting multiple systems
- Decoupled architecture

### 4. Recommended Hybrid Approach

Use both, appropriately:

- Unity Events: for simple, local connections (UI buttons, component callbacks)
- EventBus: for game-wide events (dice rolled, resources collected, building placed, turn ended)

Example events via EventBus:
- `DiceRolledEvent` (value, player)
- `ResourcesDistributedEvent` (player, resources)
- `BuildingPlacedEvent` (building type, position, player)
- `TurnStartedEvent` (player)
- `VictoryPointGainedEvent` (player, new total)
- `GameStateChangedEvent` (new state)

### 5. Singleton Pattern: Why and How

Use singletons for:
- Service Locator: central access point for managers
- GameManager: single game instance
- EventBus: single event dispatcher

Implementation options:

Option A: MonoBehaviour Singleton (recommended for Unity)
- Lives in scene
- Can use Unity lifecycle
- Easy to reference in Inspector
- Survives scene loads if needed

Option B: Static Singleton
- No GameObject needed
- Faster access
- No Unity lifecycle
- Harder to debug in Inspector

Recommendation: MonoBehaviour singleton for managers, static for pure services like EventBus.

### 6. Communication Flow Example

```
Player clicks "Roll Dice" button
  ↓
UIManager (Unity Event from button)
  ↓
DiceManager.RollDice()
  ↓
EventBus.Publish(new DiceRolledEvent(7))
  ↓
ResourceManager listens → Distributes resources
  ↓
UIManager listens → Updates resource displays
  ↓
PlayerManager listens → Checks if 7 (robber phase)
```

Benefits:
- UIManager doesn't know about ResourceManager
- Easy to add new listeners (e.g., achievements)
- Systems can be tested independently

### 7. Data Models vs GameObjects

Separate data from presentation:

- GameState (pure C# classes): player data, resources, board state
- GameObjects: visual representation only

Benefits:
- Easier to serialize (save/load)
- Can test logic without Unity
- Clear separation of concerns
- Easier to add networking later

### 9. Key Design Principles

1. Dependency injection: managers get dependencies via constructor or Service Locator, not direct references
2. Single responsibility: each manager does one thing
3. Event-driven: systems react to events, not direct calls
4. Data-driven: game rules in ScriptableObjects (resource costs, building rules)
5. Validation layer: separate validation from execution

### 10. Why This Architecture Works for Catan

- Turn-based: state machine handles phases cleanly
- Multiple systems: EventBus keeps them decoupled
- Complex rules: validation layer centralizes logic
- UI updates: events trigger UI refreshes automatically
- Extensibility: easy to add features (development cards, expansions)
- Testability: logic separated from Unity, easier to unit test

### Summary

- Use a Manager-based architecture with a Service Locator
- Implement a state machine for game phases
- Use EventBus for cross-system communication; Unity Events for simple UI callbacks
- Use singletons for core services (GameManager, EventBus)
- Separate data models from visual representation
- Make systems event-driven and decoupled

================================================================================
2. ARCHITECTURE RULES & GUIDELINES
================================================================================

SINGLETON PATTERN RULES
-----------------------
1. Use MonoBehaviour singleton for managers that need Unity lifecycle
2. Use static singleton for pure services (EventBus)
3. All singletons must have Instance property
4. Access pattern: ManagerName.Instance.Method()
5. Never use FindObjectOfType to get singletons
6. Initialize singletons in Awake(), not Start()
7. Check for null before using singleton Instance

Example Pattern:
  public class GameManager : MonoBehaviour
  {
      private static GameManager _instance;
      public static GameManager Instance => _instance;
      
      private void Awake()
      {
          if (_instance != null && _instance != this)
          {
              Destroy(gameObject);
              return;
          }
          _instance = this;
          DontDestroyOnLoad(gameObject); // if needed
      }
  }


EVENT SYSTEM RULES
------------------
1. All game events must inherit from base event class
2. Event names must end with "Event" (e.g., DiceRolledEvent)
3. Events must be in Scripts/Events/ folder
4. Subscribe in OnEnable(), Unsubscribe in OnDisable()
5. Always check for null before invoking event handlers
6. Events should contain minimal data (prefer IDs over full objects)
7. Use EventBus for cross-system communication
8. Use Unity Events for simple UI callbacks
9. Never subscribe to events in constructors (MonoBehaviour issue)
10. Unsubscribe from all events to prevent memory leaks

Event Naming Convention:
  - Action events: VerbPastTense + Event (DiceRolledEvent, BuildingPlacedEvent)
  - State events: Noun + ChangedEvent (GameStateChangedEvent, ResourceChangedEvent)
  - Request events: Noun + RequestEvent (BuildingValidationRequestEvent)


MANAGER COMMUNICATION RULES
----------------------------
1. Managers should NOT directly reference other managers
2. Use EventBus for inter-manager communication
3. Use ServiceLocator pattern if direct access is needed
4. Managers can query other managers for read-only data
5. All state changes must go through the owning manager
6. Managers should publish events for all significant state changes

Example:
  ❌ BAD: ResourceManager directly calls UIManager.UpdateResources()
  ✅ GOOD: ResourceManager publishes ResourceChangedEvent, UIManager subscribes


DATA MODEL RULES
----------------
1. Models must be pure C# classes (no MonoBehaviour, no Unity dependencies)
2. Use properties, not public fields (except for simple enums)
3. All models should be serializable
4. Models should not contain game logic
5. Models should not reference GameObjects
6. Keep models in Scripts/Models/ folder
7. Use readonly where possible
8. Implement equality comparison if needed

Example:
  public class PlayerData
  {
      public int PlayerID { get; private set; }
      public Color PlayerColor { get; private set; }
      public ResourceInventory Resources { get; private set; }
      
      public PlayerData(int id, Color color)
      {
          PlayerID = id;
          PlayerColor = color;
          Resources = new ResourceInventory();
      }
  }


VALIDATION RULES
----------------
1. All game actions must be validated before execution
2. Validation logic must be centralized (not scattered)
3. Validation should return clear error messages
4. Never execute invalid actions
5. Validation should be fast (no expensive operations)
6. Separate validation from execution

Validation Pattern:
  public bool CanPlaceBuilding(BuildingType type, Vector3 position, int playerID)
  {
      // Check all rules
      if (!HasEnoughResources(playerID, type)) return false;
      if (!IsValidPosition(position)) return false;
      if (!RespectsDistanceRule(position)) return false;
      return true;
  }


STATE MACHINE RULES
-------------------
1. Only one state can be active at a time
2. State transitions must be explicit
3. Each state must define allowed actions
4. State changes must publish events
5. State machine must handle all edge cases
6. Use enum for states, switch/state pattern for transitions
7. Validate state transitions

State Transition Pattern:
  public void ChangeState(GamePhase newState)
  {
      if (!CanTransitionTo(newState))
      {
          Debug.LogWarning($"Cannot transition from {currentState} to {newState}");
          return;
      }
      
      GamePhase oldState = currentState;
      currentState = newState;
      OnStateExited(oldState);
      OnStateEntered(newState);
      EventBus.Publish(new GameStateChangedEvent(oldState, newState));
  }

1. High-level systems depend on low-level systems
2. Never create circular dependencies
3. Use dependency injection where possible
4. Prefer composition over inheritance
5. Keep dependencies minimal

ERROR HANDLING RULES

5. Provide meaningful error messages

PERFORMANCE RULES

EVENTBUS IMPLEMENTATION REQUIREMENTS
-------------------------------------
The EventBus must support:
1. Subscribe<T>(Action<T> handler) where T : IEvent
2. Unsubscribe<T>(Action<T> handler)
3. Publish<T>(T event) where T : IEvent
4. Clear() method to remove all subscriptions
5. Debug logging (optional, can be toggled)

EventBus should be:
- Thread-safe (if needed, but Unity is single-threaded for game logic)
- Fast (use Dictionary for O(1) lookups)
- Type-safe (use generics)
- Centralized (single instance)

UNITY EVENTS vs EVENTBUS
-------------------------
Use Unity Events for:
- UI button callbacks
- Inspector-assignable callbacks
- Simple component-to-component communication
- Local, tightly-coupled connections

Use EventBus for:
- Cross-system communication
- Game-wide events
- Decoupled system communication
- Events that multiple systems need to know about

Example:
  // Unity Event (button click)
  [SerializeField] private UnityEvent onButtonClicked;
  
  // EventBus (game event)
  EventBus.Publish(new DiceRolledEvent(7));


EVENT DATA GUIDELINES
---------------------
1. Keep event data minimal
2. Prefer IDs over full objects
3. Include only necessary information
4. Make events immutable (readonly properties)
5. Add timestamp for debugging
6. Include source ID if relevant

Good Event:
  public class BuildingPlacedEvent : IEvent
  {
      public int PlayerID { get; }
      public BuildingType Type { get; }
      public Vector3 Position { get; }
      public float Timestamp { get; }
      
      public BuildingPlacedEvent(int playerID, BuildingType type, Vector3 position)
      {
          PlayerID = playerID;
          Type = type;
          Position = position;
          Timestamp = Time.time;
      }
  }

Bad Event:
  public class BuildingPlacedEvent : IEvent
  {
      public Player FullPlayerObject { get; }  // Too much data
      public GameObject BuildingGameObject { get; }  // Unity dependency
      public Dictionary<string, object> ExtraData { get; }  // Unclear
  }

7. COMMON PATTERNS & ANTI-PATTERNS
================================================================================

GOOD PATTERNS
-------------

1. Event-Driven Architecture:
   Systems communicate through events, not direct calls.
   ✅ Manager publishes event → Other systems subscribe

2. Manager Pattern:
   Single manager per system, responsible for one domain.
   ✅ ResourceManager handles all resource operations

3. Service Locator:
   Centralized access to managers (optional).
   ✅ ServiceLocator.Get<ResourceManager>()

4. State Pattern:
   Use state machine for game phases.
   ✅ GameManager manages state transitions

5. Command Pattern:
   For undo/redo (future feature).
   ✅ ICommand interface, CommandManager

6. Observer Pattern:
   EventBus implements this.
   ✅ Subscribe/Unsubscribe to events


ANTI-PATTERNS TO AVOID
----------------------

1. God Object:
   ❌ One class that does everything
   ✅ Split into focused managers

2. Tight Coupling:
   ❌ ManagerA directly calls ManagerB.Method()
   ✅ ManagerA publishes event, ManagerB subscribes

3. Circular Dependencies:
   ❌ ManagerA depends on ManagerB, ManagerB depends on ManagerA
   ✅ Use events or restructure dependencies

4. Singleton Abuse:
   ❌ Making everything a singleton
   ✅ Only core services are singletons

5. Public Fields:
   ❌ public int resources;
   ✅ public int Resources { get; private set; }

6. Magic Numbers:
   ❌ if (resources > 7)
   ✅ if (resources > MAX_RESOURCES_BEFORE_DISCARD)

7. Hardcoded Values:
   ❌ if (playerID == 0)
   ✅ Use constants or configuration

8. Mixing Concerns:
   ❌ BuildingManager also handles UI updates
   ✅ BuildingManager handles logic, UIManager handles UI

9. Ignoring Events:
   ❌ Directly modifying state without events
   ✅ Always publish events for state changes

10. Memory Leaks:
    ❌ Subscribing to events but never unsubscribing
    ✅ Always unsubscribe in OnDisable()


COMMON MISTAKES
---------------

1. Forgetting to unsubscribe from events → Memory leaks
2. Accessing singleton before initialization → NullReferenceException
3. Modifying collections while iterating → InvalidOperationException
4. Not validating inputs → Bugs and crashes
5. Mixing game logic with UI code → Hard to test
6. Using Update() for everything → Performance issues
7. Not handling edge cases → Game breaks in unexpected situations
8. Copy-pasting code instead of reusing → Maintenance nightmare


BEST PRACTICES SUMMARY
----------------------
1. Keep systems decoupled (use events)
2. Single responsibility per class
3. Validate everything
4. Publish events for state changes
5. Keep models pure (no Unity dependencies)
6. Use singletons sparingly
7. Document complex logic
8. Test edge cases
9. Handle errors gracefully
10. Follow naming conventions
